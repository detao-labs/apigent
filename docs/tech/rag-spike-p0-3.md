# Spike 报告 — P0-3 中文稀疏检索方案

> **日期：** 2026-09-22 ｜ **对应任务：** P0-3（[rag-package-tasks.md](../modules/rag-package-tasks.md)）
> **结论：** 采用 **E —— 应用侧 jieba 分词（`cutForSearch`）+ 标识符归一化**，数据库侧保持零扩展。
> **说明：** 本文只保留决策所需的对照数据；一次性探查脚本已删除。

---

## 1. 候选总览

中文稀疏检索共六个候选。现状 / A / B 为 **SQL 侧实测**，E 为 **Node 侧实测**，C / D 受目标镜像限制无法实测，只做部署成本判断。

| 候选                                                | 中文关键词召回                           | 标识符 / 英文召回       | 部署依赖                       | 索引体积                | 判定                       |
| --------------------------------------------------- | ---------------------------------------- | ----------------------- | ------------------------------ | ----------------------- | -------------------------- |
| **现状**：`to_tsvector('english')` + 原样 setweight | 33% hit@1 / **67% 空召回**（33% 是假象） | 精确 100% / **松散 0%** | 无                             | 1.0×                    | ❌ 实测不成立              |
| **A**：标识符归一化，中文交给 dense                 | 0%（稀疏不参与）                         | 100% / 0% 空召回        | 无                             | 1.0×                    | ⚠️ 中文召回全押在 dense    |
| **B**：标识符归一化 + CJK bigram                    | 92% hit@1 / 100% hit@3                   | 100% / 0% 空召回        | 无（纯 SQL 函数）              | 2.4× tsvector / 2× 索引 | ✅ 可用，作为备选 provider |
| **C**：`pg_bigm` 扩展                               | 未实测                                   | 未实测                  | 需装扩展                       | 未实测                  | 与 B 同思路，多付扩展代价  |
| **D**：`pg_jieba` / `zhparser` 扩展                 | 未实测                                   | 未实测                  | 需装扩展 + 编译工具链          | 未实测                  | 自托管门槛最高             |
| **E**：应用侧 jieba（Node 进程内）                  | 与 B 持平（见 §4.3）                     | 同 A/B（仍需归一化）    | 无 DB 扩展；1 个 native npm 包 | 0.71×（比 B 小 30%）    | ✅ **采用**                |

**分数之外的三件事：**

1. **自托管门槛** —— C / D 要求用户在自己**数据库服务器**上装 C 扩展；E 只是 Node 侧一个包，用户不需要装数据库扩展、也不需要编译任何东西。
2. **PG 大版本绑定** —— C / D 每次升 PostgreSQL 大版本都要重新编译。
3. **版本漂移** —— E 的切分结果依赖词典 / 库版本，必须用 `tokenizer_version` 兜住（见 §6）；B 是数学定义，无此问题。

## 2. 环境实测：为什么数据库侧扩展路线被排除

目标环境：`pgvector/pgvector:pg17`，PostgreSQL 17.10（Debian 12，aarch64）。

`pg_available_extensions` 实际内容：

| 扩展                                | 可安装          | 已安装   |
| ----------------------------------- | --------------- | -------- |
| `vector`                            | ✅ 0.8.6        | ✅ 0.8.6 |
| `pg_trgm`                           | ✅ 1.6          | —        |
| `unaccent`                          | ✅ 1.1          | —        |
| `pg_bigm` / `zhparser` / `pg_jieba` | ❌ **均不可用** | —        |

即：该镜像是**官方 `postgres:17` + pgvector**，不含任何中文分词的第三方扩展源码。

尝试从源码编译 `pg_jieba`（未得出编译结论，网络中断），但过程已量化成本：

| 步骤                            | 实测结果                                                          |
| ------------------------------- | ----------------------------------------------------------------- |
| 基座自带 server 头文件 / 编译器 | ❌ 全缺（无 `postgres.h`，无 `gcc` / `make` / `git`）             |
| 装 `build-essential` + `git`    | ✅ 但依赖树数百 MB、约 3 分钟                                     |
| 装 `postgresql-server-dev-17`   | ⚠️ PGDG / Debian 12 上会拉入 `clang-19` / `llvm-19-dev`，下载中断 |

> **部署注意（附带发现）：** 应用账号 `apigent` 在库里是 **superuser**（`rolsuper = true`）。`CREATE EXTENSION vector` 需要该权限，所以开发环境能跑通；生产环境不应如此——**扩展安装必须是部署 / 迁移步骤，不是应用启动步骤**。

## 3. 现状为什么不可用（根因）

`ts_debug('simple', '订单退款接口 POST /orders/{id}/refund 退款')` 的实际切分：

| 类型        | token          |
| ----------- | -------------- |
| `word`      | `订单退款接口` |
| `asciiword` | `POST`         |
| `file`      | `/orders`      |
| `asciiword` | `id`           |
| `file`      | `/refund`      |
| `word`      | `退款`         |

两个问题同时暴露：

1. **连续 CJK 被当成一个 `word`** —— `退款` 查不到 `订单退款接口`；`english` 与 `simple` 对中文行为一致，换配置无效。
2. **path 被识别为 `file` 类型** —— `/orders` 是单个 token，`orders` 查不到它。

因此设计文档里「给 `path` 加 A 级权重」只在**查询串与 path 字面完全一致**时有效。直接实测：`退款` / `订单` / `refund` / `orders` 全部**未命中**。

## 4. 对照评测

### 4.1 方法

目标库为空（`endpoints` / `business_contexts` / `knowledge_chunks` 均 0 行），故使用手写语料：**25 条 chunk**（18 个中文接口 + 6 个 tag 概述 + 1 个全局约定），**29 条查询**分六类。

- **SQL 侧对照**（§4.2）：三个变体共用同一语料与同一套字段权重（A/B/C），只改变换方式。V1 = 现状，V2 = 标识符归一化，V3 = V2 + CJK bigram。
- **Node 侧对照**（§4.3）：四种中文处理策略，标识符归一化四者共用。
- **范围**：只测稀疏一路。dense 需 embedding provider（`getEmbedding()` 未实现），不在本轮。

### 4.2 SQL 侧：三种变换

格式 = hit@1 / 空召回率（括号内为 MRR）。

| 查询类别       | n   | V1 现状                | V2 归一化          | V3 归一化 + bigram    |
| -------------- | --- | ---------------------- | ------------------ | --------------------- |
| 精确标识符     | 4   | 100% / 0%（1.000）     | 100% / 0%（1.000） | 100% / 0%（1.000）    |
| **松散标识符** | 5   | **0% / 100%（0.000）** | 100% / 0%（1.000） | 100% / 0%（1.000）    |
| 英文词         | 4   | 100% / 0%（1.000）     | 100% / 0%（1.000） | 100% / 0%（1.000）    |
| **中文**       | 12  | **33% / 67%（0.333）** | 0% / 100%（0.000） | **92% / 0%（0.958）** |
| 中英混合       | 1   | 0% / 100%（0.000）     | 100% / 0%（1.000） | 100% / 0%（1.000）    |
| 改写式中文     | 3   | 0% / 100%（0.000）     | 0% / 100%（0.000） | 0% / 67%（0.167）     |
| **总 MRR**     | 29  | **0.414**              | **0.483**          | **0.897**             |

资源代价：tsvector 总字符 V1 2 322 / V2 2 215 / **V3 5 559（2.4×）**；GIN 索引 16 kB / 16 kB / **32 kB（2×）**。

| 取消订单           | e03  | e03      | ∅        | e03, e01                 |

### 4.3 Node 侧：四种中文处理策略

jieba 通过 `@node-rs/jieba` 引入——Rust / napi **预编译二进制**，`npm install` 9 秒，无编译过程。

**切分质量：jieba 优于 Node 内置的 ICU。**

| 原文             | ICU `Intl.Segmenter` | jieba `cut` | jieba `cutForSearch`    |
| ---------------- | -------------------- | ----------- | ----------------------- |
| 查询账户**余额** | 余 / 额 ❌           | 余额 ✅     | 余额 ✅                 |
| 创建**发货单**   | 发 / 货 / 单 ❌      | 发货单 ✅   | 发货 / 货单 / 发货单 ✅ |
| 使用**优惠券**   | 优惠 / 券 ❌         | 优惠券 ✅   | 优惠 / 优惠券 ✅        |

**检索指标：jieba 没有超越 bigram，默认模式反而更差。**

> 口径说明：本节是「任意词元交集」的粗判（11 条中文查询），与 §4.2 的 SQL 侧排序指标（12 条中文、含 `ts_rank`）**口径不同，只能横向比较**，不能跨表对数字。

| 策略                     | 中文查询命中   | tsvector 字符 | 相对 bigram | 误召回接口数 |
| ------------------------ | -------------- | ------------- | ----------- | ------------ |
| **bigram**               | 11 / 11        | 1 499         | 1.00×       | **54**       |
| ICU `Intl.Segmenter`     | 11 / 11        | 1 041         | 0.69×       | 67           |
| jieba `cut`              | **10 / 11** ⚠️ | 1 012         | 0.68×       | 62           |
| **jieba `cutForSearch`** | **11 / 11**    | 1 066         | **0.71×**   | 66           |

**最关键的发现：jieba 默认 `cut` 会掉召回。** 它把文档里的「发货单」切成**单个词元**，而用户查「发货」→ 两个词元对不上，**命中 0**。必须用 `cutForSearch`（搜索模式）才能恢复——`cutForSearch` 会把「发货单」同时输出 `发货` / `货单` / `发货单` 这类重叠子词。

> **一般的道理**：切得太碎只是退化成 bigram（不致命）；**切得太 "准" 太长反而会丢召回**。决定成败的不是分词器多聪明，而是**切分模式与召回目标是否匹配**。

## 5. 关键发现

1. **V1 的「中文 33%」是假象** —— 命中的几条都是「查询串恰好等于文档里被标点分隔出的片段」（summary 就叫「取消订单」，查它自己当然中）。真实用户查询（退款 / 开票 / 库存 / 发货 / 提现 / 账户余额）全部空召回，真实空召回率 67%。
2. **V1 在「松散标识符」上 100% 失效，这比中文问题更严重** —— 用户或 LLM 写 `orders refund` 而非 `POST /orders/{id}/refund` 就完全找不到。根因是 path 被切成单个 `file` token。**标识符归一化无条件采纳**，与中文方案无关。
3. **jieba 默认 `cut` 会静默掉召回** —— 「发货」查不到「发货单」。不报错、不告警，是本方案最容易埋雷的地方。
4. **bigram 的噪音主要在 rank 2/3** —— `优惠券怎么用` 的 top-1 错成「查询优惠券」，「退款」的第二位是「取消订单」（其描述提到退款）。要靠 RRF + 精排收尾。
5. **改写式查询全部失守** —— 「把钱取出来」「如何撤销已经下的单」在四种策略下基本全灭。**稀疏不能替代 dense**；反过来 A 的中文 0% 也说明 **dense 不能替代稀疏**，两者互补。

---

## 6. 决策与必须遵守的约束

**决策：采用 E —— 应用侧 jieba 分词（`cutForSearch`）+ 标识符归一化，数据库侧零扩展。**

理由：否掉 D 的核心理由是「要往数据库服务器装 C 扩展」，而这个理由**对 E 不成立**；同时 jieba 的分词质量实测优于 ICU，索引体积比 bigram 小约 30%，且 `@node-rs/jieba` 是预编译二进制，用户无需编译任何东西。

**三条硬约束（缺一不可，否则静默劣化）：**

1. **必须用 `cutForSearch`，不得用默认 `cut`** —— 实测默认模式在「发货」这类查询上命中为 0。写进代码注释与单测。
2. **索引必须记录 `tokenizer_version`**（库版本 + 词典版本 + 分词模式），检索时校验，不一致则拒绝检索或强制重索引。
3. **分词器是进程级单例**，词典常驻内存；平台 / worker / MCP 网关三个进程各加载一次，需确认内存与冷启动开销可接受。

**存储形态（消除应用侧分词的短板）：** 应用写入切好词的 `search_text`，`search_vector` 由它派生为 generated column：

```
应用（jieba）→ search_text → search_vector
                              GENERATED ALWAYS AS
                              (to_tsvector('simple'::regconfig, search_text)) STORED
```

这样 tsvector 仍在 DB 侧确定性生成，**保留纯 SQL 可调试性**（可直接 `select search_text` 看切成了什么），不必起应用。

**保留 `pg-fts-bigram` 作为备选 provider** —— 零依赖、无版本漂移，实现只有一段 SQL，作为逃生通道成本极低。

---

## 7. 局限

1. **没测 dense。** 无 embedding provider，因此 E 的价值里有多少会被 dense 覆盖，未知。待 M2 落地后用同一套语料与查询集补一轮混合检索评测。
2. **语料是手写的，不是真实导入的 spec。** 目标库为空，无法用真实数据评测。
3. **规模极小。** 25 条 chunk、29 条查询，足以判断「能不能命中」这类定性差异，不足以判断大规模下的延迟与索引膨胀曲线。
4. **C / D 未测质量，D 的编译可行性未验证。** 对它们的判断是**部署成本判断**，不是质量结论。
5. **Node 侧「误召回接口数」是粗粒度指标**（任意词元交集计数，不含 `ts_rank` 排序质量），只能横向比较，不能当作真实排序质量。
6. **`ts_rank` 用默认权重**，未调优；实现时可能需要在 RRF 前对分数做归一化。

## 附：对既有设计文档的修正

[semantic-search.agent.md](../modules/semantic-search.agent.md) §2.2 的 BM25 方案实测不成立，该节已加证伪提示：

1. `to_tsvector('english', …)` 不切分中文；
2. `setweight(path, 'A')` 因 `file` token 而只在字面全等时生效；
3. 文中「`tsvector` Generated Column 自动同步、无窗口期」与实现不符——迁移里它是普通列；且一参形式 `to_tsvector(text)` 是 STABLE，不能用于 generated column。
